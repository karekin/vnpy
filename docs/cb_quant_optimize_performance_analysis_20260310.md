# CB Quant 优化任务性能分析与优化方案（2026-03-10）

## 1. 结论摘要

这轮优化任务跑得慢，根因不是单一的“代码写得不够快”，而是以下几个问题叠加：

1. 当前执行模型的并发度太低。
2. 单个参数组合的计算成本本身很高。
3. 当前任务全部是 `1y` 单窗口，导致现有两阶段粗筛机制完全没有生效。
4. 系统把一次实验拆成了数百个独立优化任务，但每个任务又不能继续切分成更细的执行分片。
5. 代码中确实存在一部分可避免的重复计算，但目前主矛盾仍然是真实计算量过大与执行模型不匹配。

基于本地数据库与当前代码实现，结论是：

- 这不是 UI 假象，也不是“任务其实没在跑”。
- 这批任务确实有很大的真实计算量，没有明显“九成都是水分”这种情况。
- 但也确实存在结构性浪费，尤其是单窗口任务无法启用粗筛、每个组合重复构造整段历史候选池、实验抽象过细导致任务数膨胀。
- 现阶段不建议立刻上阿里云 SchedulerX 之类的分布式跑批平台作为第一步。
- 正确顺序应该是：先把单机执行模型与任务拆分模型做对，再决定是否接入分布式调度。

## 4. 为什么计算量会这么大

### 4.1 外层并发只有 4 个执行槽位

优化任务和普通回测任务共用一个全局线程池：

- `ThreadPoolExecutor(max_workers=4)`

相关代码：

- `vnpy/web/services/cb_quant_service.py:131`

创建优化任务后，真正的执行入口 `_run_optimize_task(...)` 是直接提交到这个线程池里的：

- `vnpy/web/services/cb_quant_service.py:880`

这意味着：

- 同一时刻最多只有 `4` 个优化任务能真正开始执行；
- 剩下的 `356` 个任务只能处于 `queued` 状态等待。

这不是调度器坏了，而是线程池本来就只有 4 个槽位。

### 4.2 单个任务内部默认仍然是串行评估组合

每个优化任务内部，组合评估并发数来自：

- `CBQ_OPT_WORKERS`

默认值是：

- `1`

相关代码：

- `vnpy/web/services/cb_quant_service.py:2984`
- `vnpy/web/services/cb_quant_service.py:3054`

本机当前没有设置任何 `CBQ_*` 相关环境变量，因此这里使用的是默认值。

这意味着当前实际运行模式接近于：

- 外层：最多并行 4 个优化任务
- 内层：每个优化任务内部串行扫参数组合

所以从系统行为上看，它更像“4 条单线程流水线”，而不是一个真正的高吞吐批量计算系统。

### 4.3 单个组合不是轻任务，而是重任务

`_evaluate_combo(...)` 的核心流程是：

1. 根据当前组合构造策略参数
2. 为整段历史的每个交易日构造候选池代码映射 `candidate_code_map`
3. 再基于这个候选池映射跑回测

相关代码：

- `vnpy/web/services/cb_quant_service.py:3211`
- `vnpy/web/services/cb_quant_service.py:3264`

其中，`candidate_code_map` 的构造是：

- 对 `dataset` 里的每一个交易日
- 调一次 `cb_backtest.build_candidates(...)`

相关代码：

- `vnpy/web/services/cb_quant_service.py:3161`

而 `build_candidates(...)` 内部又会：

1. 拷贝当日 DataFrame
2. 做基础过滤
3. 做多个因子打分
4. 做动态因子打分
5. 再按 `weight_score` 排序

相关代码：

- `vnpy/web/core/cb_backtest/portfolio_backtest.py:157`
- `vnpy/web/core/cb_backtest/candidate_selection.py:120`
- `vnpy/web/core/cb_backtest/candidate_selection.py:296`
- `vnpy/web/core/cb_backtest/candidate_selection.py:324`

这说明一个“组合评估”不是一次简单公式计算，而是一次“整段历史逐日筛债 + 回测”的重计算。

### 4.4 当前历史数据规模已经足够把单组合成本拉高

快照库 `cb_daily_snapshot` 当前规模：

- 总快照行数：`402,970`
- 覆盖日期：`2022-10-24` 到 `2026-03-10`
- 全量交易日数：`819`
- 全量原始快照的平均每日行数：约 `492`

需要特别说明：

- 上面的 `492` 只是“原始日快照行数均值”，不是“可参与筛债的有效债券数”。
- 它没有扣除基础过滤后的不可用标的，也没有显式扣除停牌标的。

按当前优化任务真正使用的 `1y` 窗口重新统计：

- 最近一年的交易日数约 `244`
- `1y` 窗口原始快照平均每日行数：约 `434.6`
- 经过 `filter_multiple_factors(...)` 第一层基础过滤后的平均每日样本数：约 `424.9`
- 如果再用 `close_price > 0` 且 `volume_hand > 0 or turnover_amount_wan > 0` 作为“近似可交易”代理，则平均每日样本数约 `423.0`

因此，一个 `1y` 组合更合理的估算口径应当是：

- 原始快照口径：`244 x 434.6 ≈ 106,042`
- 过滤后有效样本口径：`244 x 424.9 ≈ 103,675`
- 近似可交易口径：`244 x 423.0 ≈ 103,212`

其中最后一个“近似可交易口径”仍然只是代理值，不是严格的“可成交证券数”，因为当前快照和筛债逻辑里没有单独使用一个明确的“停牌/不可交易”字段做过滤。

而当前待跑组合数约：

- `251,402`

换算下来，待处理数据点规模大约是：

- 按原始快照口径：`106,042 x 251,402 ≈ 26.7 billion`
- 按过滤后有效样本口径：`103,675 x 251,402 ≈ 26.1 billion`

也就是说，即便改用更保守、更接近真实可筛样本的口径，仍然是 `261` 亿级以上的“债券-交易日”处理单元。

在这个量级下，4 条串行 worker 跑很多天是正常现象，不是偶发卡顿。

### 4.5 已完成任务的真实耗时也证明任务很重

从已完成的 `18` 个任务反推：

- 已完成组合数合计：`29,359`
- worker 分钟数合计：`7,977`
- 平均每个 worker 每分钟只能处理约 `3.68` 个组合
- 平均每个组合约耗时 `0.272` 分钟，即约 `16.3` 秒

已完成任务中有一些典型样本：

- `150` 组合任务，耗时约 `357` 分钟
- `3,000` 组合任务，耗时约 `754` 分钟
- `4,800` 组合任务，耗时约 `1,434` 分钟
- `4,800` 组合任务，耗时约 `1,807` 分钟

这说明：

- 大任务确实可以跑到 1 天以上；
- 不是因为队列没动，而是单个任务本身就很重。

按照当前经验吞吐估算：

- 剩余 `251,402` 个组合
- `4` 个执行槽位
- 每个 worker 每分钟约 `3.68` 个组合

理论剩余时间约：

- `11.9` 天

所以“两天只跑完十几个任务”与当前架构是吻合的。

## 5. 有没有“水分”？是否存在明显的无效计算

结论先说：

- 有真实计算量，不是大部分都在空转。
- 但也确实存在不小的结构性浪费。

下面分三类说明。

### 5.1 不属于“水分”的部分：这些计算大多是真活

以下部分虽然重，但大部分是业务上真实需要的：

1. 每个组合都要对整段历史逐日筛债。
2. 每个交易日都要做多因子过滤、打分、排序。
3. 候选池生成后还要逐日回放持仓、调仓、止盈止损。

这些计算并不是纯粹的低级失误，而是当前“可转债日频多因子回测”业务模型天然的成本。

所以不能简单认为“只要稍微优化下 Python 写法就能快十倍”。

### 5.2 属于明显浪费的部分：当前确实做了不少可避免的重复计算

#### 5.2.1 单窗口任务完全绕过了粗筛

当前粗筛启用条件强依赖 `len(windows) >= 2`：

- `vnpy/web/services/cb_quant_service.py:2987`

这会导致：

- `1y` 任务哪怕有 `6400` 个组合，也不会先抽样再复评；
- 而是直接把全部组合完整跑一遍。

这不是业务必然要求，更像是当前实现为了简化逻辑做的约束。

这是目前最明显的“有水分”的计算来源之一。

#### 5.2.2 每个组合都会重新逐日构造整段历史候选池

`_evaluate_combo(...)` 中每个组合都要重新生成 `candidate_code_map`：

- `vnpy/web/services/cb_quant_service.py:3264`

也就是说：

- 同一任务内相邻两个组合，哪怕只改了一个阈值；
- 也会重新遍历整段 `1y` 历史的每个交易日；
- 再重新做一遍筛债、打分、排序。

这在业务上是正确的，但在工程实现上非常昂贵。

这里最大的浪费不是“算错了”，而是“缺少中间层缓存与向量化表达”。

#### 5.2.3 每个交易日都在重复构造派生因子和拷贝 DataFrame

`filter_multiple_factors(...)` 每次都会重新计算：

- `days_elapsed`
- `days_remain`
- `premium_score`
- `price_score`
- `pb_score`
- `option_score`
- `outstanding_amount_score`
- `market_cap_score`
- `volatility_score`
- 各类动态因子输入和动态打分

同时还会：

- `df.copy()`
- 列回填
- `sort_values(...)`

相关代码：

- `vnpy/web/core/cb_backtest/candidate_selection.py:172`
- `vnpy/web/core/cb_backtest/candidate_selection.py:284`
- `vnpy/web/core/cb_backtest/candidate_selection.py:296`
- `vnpy/web/core/cb_backtest/candidate_selection.py:324`

这些工作如果能预先转成按日缓存的数值矩阵，就不需要在每个组合里重复做一遍。

#### 5.2.4 任务结果状态会周期性写 SQLite，但这不是主瓶颈

优化过程中会周期性调用 `_update_optimize_task(...)`，写回 SQLite：

- `vnpy/web/services/cb_quant_service.py:2849`

不过当前写频率是按关键节点或固定步长控制的，并不是每个组合都写：

- `vnpy/web/services/cb_quant_service.py:2159`
- `vnpy/web/services/cb_quant_service.py:2310`

而且 `cb_optimize_task.row_json` 长度只有约 `700` 多字节，单条写入并不大。

因此：

- 这是次要开销；
- 可以优化；
- 但不是这次慢到跑两天的主根因。

### 5.3 属于抽象问题的部分：不是代码漏洞，但模型设计不合理

#### 5.3.1 “策略模板”承担了太多职责

当前系统里，“模板”既像：

- 策略定义

又像：

- 参数空间定义

还在前端操作上变成了：

- 一次实验中的最小投递单位

结果就是：

- 一次实验里启用 `378` 个策略模板
- 前端就会直接创建 `378` 个优化任务

相关代码：

- `frontend/src/app/(admin)/cb-quant/backtest-evaluation/page.tsx:746`

这说明系统缺少一个更高层的抽象：

- “实验批次 / study / experiment batch”

如果没有这个层，系统就只能把一次大实验拍扁成几百个独立任务。

#### 5.3.2 优化任务本身又不能再继续切分

当前一个 `OPT-*` 任务内部虽然会遍历很多组合，但这个任务对象本身没有“分片”概念。

也就是说系统缺少：

- combo range shard
- partial result merge
- shard retry
- shard checkpoint

这会导致两类问题：

1. 单任务太重，容易跑几个小时甚至一天。
2. 外部调度系统即使接进来，也只能调度大任务，不能精细扩缩容。

#### 5.3.3 外层 4 线程 + 内层默认 1 线程，本质上不是批处理架构

当前结构更像：

- Web 服务里顺手挂了一个线程池

而不是：

- 真正的批量计算框架

这在任务量小时可以工作，但当一次实验直接入队 `378` 个重任务时，就会暴露为明显的吞吐瓶颈。

## 6. 判断：现在该不该直接上 SchedulerX

结论：

- 长期看，可以考虑。
- 但现在不应该把它作为第一步。

原因是当前还有两个基础问题没解决：

1. 单机执行模型还没有打满。
2. 任务对象还没有被拆成适合分布式调度的分片。

如果现在直接接 SchedulerX，得到的会是：

- 更多机器来跑同样粗粒度的大任务；
- 运维复杂度、失败重试复杂度、结果汇总复杂度显著上升；
- 但很多本地就能解决的重复计算仍然存在。

所以合理路线应该是：

1. 先做单机和单任务内部的结构优化。
2. 再把任务抽象改成“批次 + 分片”。
3. 最后才决定是否接入 SchedulerX / Celery / Argo / Ray 之类的调度层。

## 7. 技术优化方案

下面按投入与收益排序给出方案。

### 7.1 第一阶段：先把现有单机架构从“低吞吐”拉到“可用”

目标：

- 不引入外部分布式平台；
- 先把现有机器吞吐提升数倍。

#### 方案 A：把外层并发和内层并发改成可配置

当前问题：

- 外层线程池硬编码 `max_workers=4`
- 内层组合评估默认 `CBQ_OPT_WORKERS=1`

建议：

1. 把外层优化任务线程池大小改成环境变量，例如 `CBQ_TASK_WORKERS`
2. 区分普通回测任务池和优化任务池，避免互相争抢
3. 给不同机器配置不同并发档位

预期收益：

- 这是最低成本的吞吐提升方式
- 但收益受 CPU/GIL 与 pandas 行为限制，不应过度乐观

#### 方案 B：让单窗口任务也能启用 stage1 粗筛

当前问题：

- 粗筛要求 `len(windows) >= 2`
- 你当前全部任务是 `1y`

建议：

1. 改造 `_should_enable_stage1_screening(...)`
2. 对单窗口大任务同样允许先抽样再全量复评 shortlist
3. 对 `1y` 任务设置单独阈值和采样比例

预期收益：

- 对大参数空间任务会是非常直接的减负
- 这是本轮最值得优先改的点之一

#### 方案 C：降低任务对象同步与排行榜维护频率

建议：

1. 进度刷新间隔改大
2. 临时 TopN 维护改用最小堆，而不是每次 append 后全量 sort
3. 减少 `_sync_optimize_task_as_backtest_job(...)` 的触发频率

相关代码：

- `vnpy/web/services/cb_quant_service.py:2294`
- `vnpy/web/services/cb_quant_service.py:2859`

预期收益：

- 这是次级优化
- 单独收益不会很大，但实现成本低

### 7.2 第二阶段：减少单组合内部的重复计算

目标：

- 不只是“多开线程”
- 而是把每个组合真正变便宜

#### 方案 D：按交易日预计算可复用的基础特征矩阵

当前问题：

- 每个组合都会重新计算每日的基础过滤与多种因子输入

建议：

1. 对每个交易日预生成基础过滤后的 universe
2. 预计算静态或准静态特征列：
   - `close_price`
   - `conversion_premium_pct`
   - `underlying_pb`
   - `underlying_volatility`
   - `days_elapsed`
   - `days_to_maturity`
   - `outstanding_amount_yi`
   - `underlying_market_cap_yi`
   - 动态因子输入列
3. 将其保存为按日缓存的 NumPy / Arrow / Polars 结构

这样每个组合只需要：

- 代入阈值和权重
- 在数值矩阵上做快速评分和 top-k 选择

而不是重新走一次 DataFrame 级别的业务流水线。

这是中期最关键的结构优化。

#### 方案 E：把 `build_candidates` 从 DataFrame 风格改成数值核

当前问题：

- `filter_multiple_factors(...)` 写法偏分析脚本风格
- 适合可读性，不适合海量参数搜索

建议：

1. 保留一份“可读版”实现用于单次分析和验证
2. 另做一份“优化版”执行核用于参数搜索
3. 优化版执行核只输出：
   - top candidate codes
   - 必要指标
4. 避免在优化阶段回填大量中间列

这一步的本质是把：

- “研究态 DataFrame 代码”

和

- “批量搜索执行核”

拆开。

这本身就是抽象层重构。

#### 方案 F：改用进程池，而不是线程池

当前问题：

- 现在是 `ThreadPoolExecutor`
- 这类任务偏 CPU 密集，且包含大量 pandas 运算

建议：

1. 对组合评估使用 `ProcessPoolExecutor` 或独立 worker 进程
2. 避免 GIL 对 CPU 利用率的限制
3. 将大对象缓存放到共享只读内存或 worker 本地缓存中

注意：

- 这一步收益需要通过 profiling 验证
- 因为 pandas 某些底层操作会释放 GIL，但不是全部

### 7.3 第三阶段：重构任务抽象，支持真正的批量计算

目标：

- 让一次实验从“几百个大任务”变成“一个批次 + 很多可调度分片”

#### 方案 G：引入 Experiment Batch 抽象

建议新增三层概念：

1. `ExperimentBatch`
   - 表示一次用户发起的大实验
   - 例如“对 378 个策略模板做 1y 优化”
2. `OptimizeTask`
   - 表示某个模板的一次优化任务
3. `OptimizeShard`
   - 表示某个优化任务的一个组合区间分片
   - 例如 `CMB-000001~001000`

这样可以支持：

- 批次级展示
- 任务级分析
- 分片级调度与失败重试

#### 方案 H：把一个大任务拆成多个 combo-range 分片

例如一个 `6400` 组合任务，可以拆成：

- 8 个 `800` 组合分片

每个分片独立执行并回传局部 TopN，最后再汇总。

这样做的好处：

- 提升调度粒度
- 容易横向扩容
- 单次失败重试代价更低
- ETA 更准确

#### 方案 I：把最终结果汇总设计成幂等过程

需要补齐：

1. shard 状态机
2. shard 局部结果表
3. batch/task 汇总逻辑
4. 幂等重试
5. checkpoint 与断点恢复

这是未来接入分布式平台的前置条件。

### 7.4 第四阶段：在任务切分完成后，再评估是否接入 SchedulerX

当且仅当以下条件满足时，再考虑 SchedulerX 之类平台：

1. 已经有 `ExperimentBatch / OptimizeTask / OptimizeShard` 三层模型
2. 单 shard 的输入输出已经固定
3. shard 可幂等执行
4. 本地单机版本已经证明计算核是高效的

这时接入分布式调度才是放大收益，而不是放大复杂度。

可选方向包括：

- 阿里云 SchedulerX
- Celery + Redis/RabbitMQ
- Argo Workflows
- Ray
- 自建多进程 / 多机 worker 队列

但在当前阶段，它们都不是第一优先级。

## 9. 最终判断

### 9.1 慢的核心原因

根因排序如下：

1. 外层只有 4 个执行槽位
2. 内层组合评估默认串行
3. 单个组合本身是重计算
4. 单窗口任务禁用了粗筛
5. 一次实验直接创建了 378 个大任务

### 9.2 有没有明显水分

有，但不是“主要都在白算”。

更准确地说：

- 真实计算量很大，这是主因；
- 同时存在不小的可避免重复计算，这是次因；
- 再叠加任务抽象过粗、调度粒度过大，最终放大成了现在的排队问题。

### 9.3 是否应该直接采购/接入跑批平台

暂时不建议作为第一步。

先做：

1. 单机吞吐优化
2. 单窗口粗筛
3. 数值核重写
4. 任务分片

做完这些以后，再看是否需要 SchedulerX，决策会更准确，也更容易落地。
